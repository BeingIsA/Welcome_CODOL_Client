## 服务端登录、创建房间与退出房间（2026-10-22）

用户批准接入现有服务端接口，暂用 HTTP，不增加 TLS 或身份加密。新增 application/multiplayer、adapters/transport、adapters/persistence/server_identity.py、platform/machine_identity.py 和版本 multiplayer_bridge.py；由 bootstrap 装配。业务接口全部在单个后台线程执行，原生线程只提交请求与消费完成结果。登录成功后再激活大厅，建房成功后调用原生创建回调；离房失败保留原生房间，成功才清理并通知界面。未指定 --server-url 时原有离线补丁生成字节保持一致。

playerId 按服务器地址保存于 client/data/accounts/server-identities.json，重登复用；SMBIOS 系统 UUID 摘要用于机器指纹。身份文件损坏、未知身份和封禁不静默注册新号。建房前保存恢复标记，响应丢失不自动重放；下次操作或重启会查询并清理遗留房间。正常进程退出尝试离房，失败保留恢复记录。未实现 WS 在线状态、加入他人房间和对局；服务端暂不接受房间标题、地图和模式。首次登录响应丢失的身份恢复需要服务端幂等契约，当前不保证。

验证结果：39 项专项回归通过，覆盖身份重用、后台请求去重、超时与恢复、封禁、坏文件、响应契约、原生 ABI、迟到结果拒绝及架构边界。报告：verification/client/reports/multiplayer-focused-final-20261022.json。启动参数预检通过：verification/client/reports/multiplayer-dry-run-20261022.json。

真实 HTTP 联调与隔离实机通过：登录激活大厅；服务端拒绝建房后原生 session 清空；解除封禁后成功建房；拒绝离房时原生 session 保留；解除封禁后离房成功；随后再次建房并退出成功。实机使用独立账号、设置、身份和临时服务端数据库，运行产物位于 verification/client/workspaces/multiplayer-1792624183888678700/，关键证据为 report.json、native-results.json 与 runs/ 下日志。探针调用真实原生建房及 GFx 离房入口，不替代鼠标点击和弹窗视觉验收。

全量历史套件一次运行 270 项，有 3 个失败、6 个错误和 4 个跳过（verification/client/reports/multiplayer-suite-20261022.json）：历史 capture/schema 文件缺失、沙箱内受限令牌创建失败、旧安装轨迹/电影规则数量基线过时，以及源码 AST 冻结断言。针对本次 room/menu_preview 的 AST 断言已改为离线输出字节差分并通过；该历史断言随后仍在未修改的 player_name.py 上失败。未修改其他生产功能或伪造历史夹具以消除这些问题。实机受限令牌验证在获准的沙箱外运行后通过。

## 本地玩家昵称改名（2026-10-18，已实现，待实机验收）

### 首次实机失败后的字段宽度修正

会话 `offline-20261018-235046-37c7b93f/events.jsonl` 第232行确认昵称请求进入本地桥，但在request阶段被“请离开房间后改名”拒绝，未进入原生写入或SQLite保存。复核原生 `62FDC6` 的 `cmp byte ptr [ecx+38710],0`，发现本地检查误用32位读取，包含了后续两个独立状态字节与填充字节。新增独立回归用例证明相邻字节分别非零时旧实现均错误拒绝；修正为读取1字节，并将原生检查指令加入安装前ABI校验。原日志没有保存该字段快照，无法证明具体是哪一相邻字节触发了现场拒绝。15项昵称及UI测试通过，包括真实房间/待进房间仍拒绝；需要再次启动实机验收。此前夹具把相邻字节全部置零，未覆盖此问题。

用户批准完整本地改名方案后，现有 `client/v1649370/player_name.py` 接管本次 local-profile 会话的 `AS_RedeemChangeName` GFx 回调槽（`DCCB44`）。只有本地档案就绪且 DW=0 才进入宿主握手，其他状态回原 handler。宿主还核对主线程、参数类型、房间/待进入房间状态及输入长度。正式代码未新增模块，不修改共享在线任务服务、登录状态或磁盘游戏资源。

### 玩家昵称改名的 TCLS 诊断（2026-10-18，历史诊断，后续实现见上文）

用户实际测试的是玩家昵称改名，提示 `SU_UI_CHANGE_NAME_TCLS_ONLY`。该提示在整个 UI 资源中只有一处引用：`MarketController.handleRedeemChangeName` 在 `IsTCLSLogOn()` 为 false 时显示。玩家名与背包名是两条互不相交的事件链：`EVT_REDEEM_CHANGE_NAME` 仅由 `RenameConfirm` 发出、仅由 `MarketController` 接收；`EVT_SET_LOADOUT_NAME` 仅由 `FsgChangeLoadoutNamePopupView` 发出、仅由 `WeaponLoadOutController` 接收。

按用户选择先做最小诊断：新增 `client/v1649370/player_name.py`，把 `MarketController.handleRedeemChangeName` 方法内偏移 84～94 的 `IsTCLSLogOn()` 调用替换为 `pushtrue`（10 个 nop 填充），保留其后的 `iffalse` 与调试行，方法长度 178 与栈上限 `[4,3,7,8]` 不变。该替换只用于确认后续在线改名请求 `DataID.REDEEM_CHANGE_NAME` 在离线时是否有回调，**不是合法修复**；移除诊断规则前不得声称改名已可用。

即使请求有回调，成功分支仍需要 `CFunctionContainer.SavePlayerStats()` 落档，而 AS 层没有写玩家名的接口（`UserObj` 仅构造函数、`CFunctionContainer` 只有 `AS_RedeemChangeName`/`SavePlayerStats`）。完整离线改名需要 native 桥写入玩家名并构造完成结果，属独立工作。测试见 `client/tests/test_sanitize_patch.py` 的 `test_tcls_check_replaced_by_true`。
